# SSH Link: 点对点 ssh 转发作为 mesh 之外的跨机传输

Status: accepted

## Context

Mesh（ADR 0013）为跨机 handoff 提供了注册/发现/路由/离线缓冲，但它需要一台常驻引擎。点对点场景——两台互信机器、临时连通、用完即拆——不应该要求起引擎。ssh 本身就是互信通道：它自带认证、加密和 unix socket 转发（`-L`/`-R`），而本地发现（`listPeers`）只扫描 `XFER_DIR` 顶层的 `.sock` 文件——ssh 创建的转发落点天然落入该扫描，零注册代码。

## Decision

**Link 是 Mesh 的补充，不是替代。** Mesh 是跨机的主打路径：注册、发现、路由、durable queue 是它的职责，代价是一台常驻引擎。Link 只覆盖"两台已经互信、临时连通、用完即拆"的点对点场景——不建引擎、不注册、不缓冲、不发现（发现就是对端目录快照）。需要离线投递、需要目标休眠时也能排队、需要多机发现，这些都只有 Mesh 能给。

**Link 永远是双向的**：一条 Link = 一个 ssh 进程 = 双向通路。`-L` 把远端节点引进来，`-R` 把本机推出去，同一个进程、同一条命令。任何"半条隧道"都不是我们保留的形态——它不是缺省偏好问题，而是让**回程是否存在**变成发送方必须猜的东西，猜错就把结论发进虚空。

命令面（`<host>` 是任何 ssh 目标：`~/.ssh/config` 的别名、主机名，或 `user@host`）：

```
/xfer ssh in <host> [name...]   打开/扩展一条 Link：导入远端节点(-L) 且导出本机(-R)
/xfer ssh list <host>           只读探测：远端 xfer 目录与可导入的 socket
/xfer ssh status                本进程维护的 Link + 存活状态（外来的另列）
/xfer ssh down [host|name]      整台 host 的 Link 一起拆
```

- **in 是累加的，不是替换**：`in pi-nas a` 之后再 `in pi-nas b`，得到一条承载 a+b 的 Link。不加名字地重跑只做刷新。ssh 无法在运行时增删单条 `-L`，所以扩展 = 杀掉重建，imported 集合被保留。
- **为什么没有 `out`**：它只能完成"远端能发给我"这一半，解决不了"我能不能发过去"，于是又回到猜回程。把 `-R` 并入 `in` 之后，`-R` 变成单例：一台机器一条，随该 host 的 Link 生死。
- **拆除粒度 = host**（初期决定）：不能只拆一条 `-L`；真要拆一条，就杀掉重建剩下的。per-name 计数器属于"没有计数器的必要性"的复杂度。

- **方向必须显式指定，没有 `both`**：方向不是能取中间值的参数，而是"哪一边的监听对象已经存在"这个事实。两个半边的**前提不同源**（本机 socket 永远在；远端 socket 要先探测），一条命令同时断言两边，只是把两个不保证成立的假设叠起来——所以 `both` 不是权衡，是范畴错误。
- **无 TTY，因此必须免密**：spawn 的 ssh 带 `BatchMode=yes`，交互式密码提示不可能被回答（pi 的 stdin 归 TUI）。支持密钥与 ssh-agent；认证失败时把 ssh 的 stderr 翻成可执行的建议（放公钥 / ssh-add），而不是一个裸退出码。
- **生命周期 = pi 进程**：由该 pi 显式拆除（见上条），这仍是 ADR 0013 "上线单元 = 连接单元 = pi 实例" 的同一哲学——不出现"隧道活着但 pi 死了"的判死歧义。`ExitOnForwardFailure=yes` 写死；`StreamLocalBindUnlink=yes` 是**绑定时的**清理（下次建链不被远端残留 sock 阻塞），不是退出时的——死掉的 ssh 会在远端留下 `-R` 落点，由**对端的 gc** 按 orphan-sock 规则（ECONNREFUSED）收走，这是设计的清理路径而非失败。远端落点的出现也是异步的（sshd 建它晚于 ssh 就绪），建链会显式等待它落地后才报成功，否则对端发现会闪断。
- **名字冲突拒绝**：`-L` 的本地落点撞上已有本地 sock（且不是本 Link 的旧账本），或远端已有与本机真名同名的节点，命令直接拒绝。同 ADR 0013 的"先查后占、拒绝而非自动改名"；跨机名字唯一性是用户的账。注意 `-R` 的落点在**远端**，本地那个同名 sock 是转发的**目标**（本机监听器），必须存在，不参与碰撞判定。
- **`list` 与 `status` 是两件事**：`list <host>` 回答"那台机器有什么可 in"（只读探测，不建隧道）；`status` 回答"我这条 pi 现在维持着哪些 forward、它们还活着吗"。混成一条命令会让"我要连什么"和"我连了什么"共用输出，两个问题都答不好。
- **所有权写进账本**：每条 Link 的 `.json` 记 `owner`（创建它的 pi 进程 pid）。`down` 与 `session_shutdown` 只拆 `owner === 自己` 的；别人的 Link 由别人的 pi 负责，它死了以后由 gc 按 dead-link 收尾。
- **退出必须显式拆**：ssh 子进程 `unref` 后**不会**随父进程死（会被 init 收养），所以"autodispose"靠 `session_shutdown` 里显式 `sshDown`，不是靠进程树。
- **两处记录，两种角色**：本机用 `.link.<host>.json`（host/pid/owner/names/reverseAs）作为该 host 的 Link 账本——**以 host 为键**，因为一个 ssh 进程不可能拆成多条；对端则收到一条 `<本机名>.json`，标 `role: "reverse"`、`via: "ssh"`，**故意不带 pid**（那会是本机的进程号，在对端毫无意义且会让 gc 判错）。没有这条远端标记，对端会把 Link 端点当成普通本地 Peer，文档只给路径——原本的 bug 会从反方向重演。
- **gc 与 Link 的所有权边界**（本条的初版判断有误，实测后收窄）：
  - **本机 `.link.<host>.json`**：有本机 ssh pid，判据确定。死 → **先 SIGTERM 该 pid，再删账本与它声明的所有 socket**。只删文件不杀进程会把隧道变成两头都没人认领的孤儿——这比不清理更糟，所以"删账本"和"杀进程"是同一个操作的两半，不能只做一半。gc 仍然只杀账本里点名的那个 pid，不做 listener 探测、不碰不认识的进程；`/xfer doctor` 只调 `planGc`，因此只读自检永远不杀东西。
  - **对端 `<myName>.json`（`role: "reverse"`）**：**gc 永不删除，只报告**。它由另一台机器上的 pi 经 ssh 写入，本机无法观测那个 pi 的死活——隧道抖动时该端点会时而应答、时而拒绝、时而挂着。曾有一次本机 gc 据此判定死亡并删除记录，结果那条 Link 其实还活着：`isLinkTarget` 随即把它当成本地 Peer，后续 handoff 又回到"给一个对方读不到的路径"。清理责任在写入者，它在 `down`/`session_shutdown` 时主动 ssh 删除。
  - 一句话：**本机拥有的记录，gc 连进程一起收；别人的记录，gc 只报告。**

## 单向隧道对 handoff 的两条硬约束

Link 的 socket 是本地的，但 socket 后面的人不在本机。ADR 0013 早已为 mesh 解决过同一个矛盾（跨机 `/tmp` 路径失效 → 文档内联进队列消息），Link 沿用同一结论，只是触发条件是"目标是 Link"而不是"传输是 mesh"：

- **文档必须内联，不能只给路径**。发送侧先照旧写本地 tmp（本地观察、日志、返回值的 `Doc:` 都是它），但检测到目标是 Link（同一个 `readPeerMetadata` 判活里能读到 `via: "ssh"`）时，把正文拼进消息帧，收端写入**自己**的 tmp 再走既有 inbound 管线。收端因此永远拿到一个本机可读的路径，下游毫不知情。
- **回程不需要判断，因为它按构造存在**。之前 `in`/`out` 各开半边的形态被否决了：它把"能不能回信"变成一个无法从本机断言的猜测，只能靠警告和降级去兜。现在两侧都能直接陈述事实——收端知道文档是内联来的、隧道是双向的；发端知道文档已内联。`task` 在 Link 上和本地一样安全，不需要任何降级建议。

**明确不做**：路由、离线缓冲、自动发现（发现 = 对端目录快照）、adapterd 支持（pi 扩展专属）。

## Considered

- 子目录物理隔离（`XFER_DIR/links/`）——否决：远端 `-R` 落点无论如何以 Peer 姿态出现在对端顶层（对端的 listPeers 我们控制不了），隔离只买到半个纯粹性，却要改两处代码。
- 自动改名落盘（落点改名成别的名字）——否决：落盘名与真名分裂，回信循环静默错投。
- 纯手动 ssh 命令——否决：与"离开 pi 进程 autodispose"矛盾。
- mesh 本身——不替代：Link 无引擎、无常驻组件，覆盖一次性点对点场景；两者并存，命令面显式区分（`/xfer <name>` 本地、`/xfer ssh` 隧道、`/xfer mesh <name>` 引擎）。

投递语义零改动：半死隧道上 ack 超时 → `unknown`，正是 `xfer_to` 为此准备的既有结论（"do not resend"）。

`out` 单向的后果要说清：远端节点收到 handoff 后回不了信——它们的回发目标是本机真名，而 `-L` 只让流量从本地发起。要回信，得在对端跑 `/xfer ssh in <本机>`，或本地同时开 `in`。这是显式方向的代价，也是它的意义。

## 实施教训（来自首次双机实测）

这一轮双机联调暴露的问题，几乎全部不是"逻辑写错"，而是**判据用错了对象**。
记录下来，因为这些错误会让任何一次跨机排查重演：

- **错在机器，不在平台。** `os.tmpdir()` 在 macOS 上是 `/var/folders/…/T`、在 Linux 上是
  `/tmp`，但真正的错误不是"记错了平台差异"，而是**在 A 机器上检查 B 机器该有的文件**。
  哪怕两端同为 Linux，只要它们的 tmpdir 不同（容器、`TMPDIR` 覆盖），同一个错误照样发生。
  跨机验证的第一原则因此不是"记住各平台的 tmpdir"，而是：
  **断言哪个文件系统上应该出现文件，就在那个文件系统上执行检查**——
  用产生它的那台机器的 `os.tmpdir()`，而不是自己的。

- **进程不会自动加载新代码。** `pi -ne -e .` 加载的是启动那一刻的模块快照；
  `git pull` 对已运行的进程完全无效。本轮双方都因此误判了五轮以上——
  一方跑着旧代码却以为在测新代码。

  判据不是孤立的 `ps -o lstart`：**它必须和"该进程启动时工作区的 HEAD"以及
  "现在工作区的 HEAD"一起出现**，三者的先后关系才说明问题：

  ```
  A = 进程启动时间（ps -o lstart）
  B = 该进程启动时工作区的 HEAD（决定了它加载的是哪份代码）
  C = 现在工作区的 HEAD（git log -1）
  B == C  → 进程跑的就是当前代码
  B != C  → 进程跑的是旧快照，B 到 C 之间的所有提交对它无效
  ```

  只报 A 而不报 B、C，仍然无法判断"它到底在跑什么"。

- **不能用短字符串验证传输完整性。** 运行时可能对出站文本做脱敏
  （观测到的形态是占位符替换），这会让 token 比对永久失真。改用整篇
  `sha256`（`docSha256` 字段 + `corrupt` outcome）。即使如此，它守的只是一个**时序区间**：

  ```
  [ 发送端取哈希 ] --------- 网络 / 帧 --------- [ 接收端落盘比对 ]
                       ↑ 这一区间内的任何改动都能被抓到
  区间之前（发送端自己的运行时脱敏）与之后（接收端本地处理）—— 都看不见
  ```

  所以 `verified` 的准确含义是"**这一段线路上没人动过它**"，而不是"文本从未被改写"。
  脱敏若发生在取哈希之前，检查会通过，损失不可见。这个边界同时写在
  `types.ts` 的字段注释、`server.ts` 的 `integrity()` 契约和比较点上。

- **裸 socket 不等于活着。** `sshDown` 立即删除 metadata，但 sshd 要等连接
  关闭才释放 `-R` 落点。真空档里 socket 存在却没有 agent——用 listener 探测
  判断会误报"活着"。正确判据是 `housed`：该 socket 旁边有没有同名 `.json`。

- **`-R` 的落点与 `-L` 的导入集不能重叠。** 同名时两条 forward 抢占同一个
  远端路径，ssh 无法解析。检查必须**无条件**执行，不能因"扩展已有 Link"跳过——
  第二次 `in` 恰恰是最容易撞上的场景。
