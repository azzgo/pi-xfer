# SSH Link — 验收检查单

三次全是同一类错误（**判据用错了对象**）之后留下的最简检查单。
每次改动 ssh Link、或在两台机器上排查它，先跑这三行。

**状态**：这套判据已在 2026-10-24 的真实双机验收中使用并通过
（mac ↔ Linux，双向 inline 落盘 + sha256 比对 + integrity: verified；
验收记录见 ADR 0021 文末）。此前正是因为没有这套判据，才有了五轮误判。

## 三行

```bash
# ① 版本：进程加载的是哪份代码（B/C），不是它何时启动（A）
git log --oneline -1                       # C = 现在工作区 HEAD
ps -o pid,lstart -p "$1"                   # A = 进程启动时间
#   A 早于 C 的提交时间 ⇒ 进程跑的是旧快照，C 之后再谈行为

# ② 落盘：在应当出现文件的那个文件系统上检查，不用自己的规则去查别人的
node -p 'require("os").tmpdir()'           # 该机器的 tmpdir（macOS ≠ /tmp）
ls -la "$(node -p 'require("os").tmpdir()')/pi-xfer-$MSG_ID.md"

# ③ 完整性：比对整篇 sha256，不比对任何短字符串
sha256sum "$(node -p 'require("os").tmpdir()')/pi-xfer-$MSG_ID.md"
#   与发送端取哈希前对同一文档算的值比较；相等 = 这一段线路上无人改动

# ④ 归因：这条到底走了哪条通道？（Link 和 mesh 的落盘文件同名）
grep -c "$MSG_ID" ~/.pi/xfer/mesh.log
#   >0 = 走了 mesh（engine 的 durable queue）；0 = 走了 ssh Link
```

## 每条背后是一次真实误判

| 检查 | 漏掉它会怎样 |
|---|---|
| ① 进程 vs HEAD | 在旧进程上验证新代码，双方各说各话，本轮持续五轮 |
| ② 正确的文件系统 | 在 Linux 上用 `/tmp` 检查 macOS 的 `/var/folders` 落盘，结论恒为"未落盘" |
| ③ 整篇哈希 | 短 token 会被运行时脱敏改写，比对永久失真；`grep` 还会命中自己写的举例文字 |

## 两条边界，别当成保证

- `sha256` 的 `verified` 只覆盖 `[发送端取哈希] → [接收端写入]` 这一区间。
  发送端自己的运行时在取哈希之前就改写正文时，哈希一致而损失不可见。
- `ps -o lstart` 单独使用无意义，必须与"启动时的 HEAD / 现在的 HEAD"一起看。

## 两个元教训（跨机排查的流程错误）

这轮双机联调里，两个问题耗掉的轮次比上面三条加起来还多：

### 返回文案要带版本可辨识性

发送端的成功文案在新旧代码里一模一样（`delivered inline` 是新加的，但
`✅ delivered to "..."` 的骨架没变），于是"发送端看起来成功"无法区分新旧。
**改动返回行为时，文案必须随之变化**——否则新旧无法区分，测试等于没测。

### 判据必须"自己查自己"

互判悖论：A 验证 B 的实现、B 验证 A 的实现，而双方都可能跑着旧代码——
这时互相验证是在验证幻觉，且每轮结论都会被下一轮推翻。

解法：**每侧只查自己收到的**。

```
我发 handoff → 我记录 msg_id → 你检查你机器上该 msg_id 的落盘
你发 handoff → 你记录 msg_id → 我检查我机器上该 msg_id 的落盘
```

零推演、零依赖对方的诚实度；两边的结果独立成立，矛盾时一眼定位是哪一端。
